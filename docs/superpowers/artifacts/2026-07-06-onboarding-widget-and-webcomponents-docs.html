A · Web Components 101

for developers new to custom elements

Custom Elements — a tag you defined

A custom element is a class that extends HTMLElement (or a subclass of it) and is registered with the browser under a hyphenated tag name. Once registered, the browser instantiates your class every time it parses that tag — same as it does for <video> or <select>.

class HelloBadge extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `<strong>Hello, ${this.getAttribute("name")}</strong>`;
  }
}
customElements.define("hello-badge", HelloBadge);
// <hello-badge name="Sakai"></hello-badge> now renders itself

The hyphen in the tag name is mandatory — it's how the HTML parser tells your element apart from a future native one.

Shadow DOM — style walls

Calling this.attachShadow({'{'} mode: "open" {'}'}) gives an element its own mini-DOM tree. CSS written inside a shadow root can't leak out, and page CSS can't leak in (except through inherited properties and CSS custom properties, which do cross the boundary on purpose — that's how Sakai widgets expose theme hooks like --sakai-dashboard-widget-bg-color).

class HelloBadge extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: "open" });
    this.shadowRoot.innerHTML = `<style>strong { color: teal; }</style><strong>Hi</strong>`;
  }
}

Why Lit exists

Lit (lit.dev) is a ~5 KB base class that answers exactly one question the platform leaves open: when a property changes, how do I re-render efficiently? It gives you a declarative render() using tagged-template HTML, a reactive static properties map, and a diffing renderer that only touches the DOM nodes that actually changed.

import { LitElement, html, css } from "lit";

class Counter extends LitElement {

  static properties = { count: { type: Number } };
  static styles = css`button { font: inherit; }`;

  constructor() { super(); this.count = 0; }

  render() {
    return html`
      <button @click=${() => this.count++}>
        Clicked ${this.count} times
      </button>
    `;
  }
}
customElements.define("my-counter", Counter);

Every <my-counter> on the page is isolated (shadow DOM), re-renders only its own template when count changes, and needs zero manual DOM manipulation. This is the exact pattern every Sakai widget builds on.

B · Sakai's Widget Architecture

verified against the current codebase

Class hierarchy

LitElement— from the lit package
└─SakaiShadowElement— @sakai-ui/sakai-element: shared shadow-DOM base, loadTranslations()
   └─SakaiDashboardWidget— title bar, move/remove buttons, content() extension point
      └─SakaiOnboardingWidget— our concrete widget (also: SakaiTasksWidget, SakaiGradesWidget, …)

Every dashboard widget is a two-line subclass: set this.widgetId in the constructor, override content(). Everything else — the card chrome, the up/down/left/right movers, the remove button, i18n loading — lives once in SakaiDashboardWidget.

i18n loading is keyed by widgetId

// SakaiDashboardWidget.js
set widgetId(value) {
  this._widgetId = value;
  loadProperties(value).then(r => this.title = r.widget_title);
}

Setting this.widgetId = "onboarding-courses" fetches the bundle at onboarding-courses.properties and pulls widget_title into the card's header — the bundle filename is the widget id, by convention, not by framework magic.

⚠ Rendering is not dynamic

SakaiWidgetPanel.getWidget(r, index) is a hardcoded switch — one case per widget id, each returning the widget's markup literally. Adding a widget always means adding a case, by design; this guide documents that as current-state rather than proposing to change it.

switch (id) {
  case "onboarding-courses":
    return html`<sakai-onboarding-widget site-id=${...} user-id=${...}></sakai-onboarding-widget>`;
  // …one case per widget…
  default: return "";
}

Catalog vs. switch vs. picker

Common misconception — the catalog in SakaiWidgets.js (getIds() / getWidgets()) looks like a registry the whole system reads from. It isn't: it is consumed only by SakaiWidgetPicker.js, the "add a widget" UI. The panel's own idea of which widgets exist for a dashboard comes from the server, in the JSON returned by DashboardController.

FileConsumed by
SakaiWidgets.jsOnly SakaiWidgetPicker — the add-a-widget list

Layout persistence happens through the same GET/PUT dashboard endpoints — there's no separate save-layout call. A user's layout is JSON under the dashboard-config preference key (PreferencesService); a site's layout is JSON under the dashboard-config site property (SiteService.save()). Course-dashboard widgets receive both site-id and user-id — data is scoped to that site but still filtered to the current user ("my tasks in this course").

webapi, not dashboard

The Maven module named dashboard (sakai-dashboard-tool) only serves two Thymeleaf shells — home_dashboard.html / course_dashboard.html — chosen by MainController based on siteService.isUserSite(siteId). It has no REST endpoints of its own. Every dashboard REST endpoint, including the new onboarding one, lives in the separate webapi module, package org.sakaiproject.webapi.controllers.

C · Build-Your-Own-Widget Guide

the real Onboarding Courses widget, step by step

Define the response shape

An OnboardingCourseStatus enum and an OnboardingCourse DTO in webapi/.../beans/ — the JSON contract the frontend renders against.

package org.sakaiproject.webapi.beans;

public enum OnboardingCourseStatus { NOT_STARTED, IN_PROGRESS, COMPLETED }
@Data @Builder @NoArgsConstructor @AllArgsConstructor
public class OnboardingCourse {
    private String id, title, siteId, dueDate;
    private OnboardingCourseStatus status;
    private int percentComplete;
}

Add the data seam — OnboardingService

An explicit interface plus a deterministic (not random) sample-data impl, so a real data source can be swapped in later without touching the controller.

@Service
public class OnboardingServiceImpl implements OnboardingService {

  private static final List<OnboardingCourse> CATALOG = List.of( /* 5 hand-picked sample courses */ );

  public List<OnboardingCourse> getCoursesForUser(String userId) {
    int count = 3 + Math.floorMod(userId.hashCode(), 3); // 3–5, stable per user
    return CATALOG.subList(0, count);
  }

  public Optional<OnboardingCourse> getCourseForUserAndSite(String userId, String siteId) {
    return getCoursesForUser(userId).stream()
        .filter(c -> c.getSiteId().equals(siteId)).findFirst();
  }
}

Expose the two REST endpoints

OnboardingController extends the package-private AbstractSakaiApiController (same base as TasksController) — session check, then delegate, nothing else.

@RestController
public class OnboardingController extends AbstractSakaiApiController {

  @Resource private OnboardingService onboardingService;

  @GetMapping("/users/me/onboarding-courses")
  public Map<String, Object> getOnboardingCourses() {
    Session session = checkSakaiSession();
    return Map.of("courses", onboardingService.getCoursesForUser(session.getUserId()));
  }

  @GetMapping("/sites/{siteId}/onboarding-courses")
  public Map<String, Object> getOnboardingCourseForSite(@PathVariable String siteId) {
    Session session = checkSakaiSession();
    Map<String, Object> data = new HashMap<>();
    onboardingService.getCourseForUserAndSite(session.getUserId(), siteId)
        .ifPresent(course -> data.put("course", course));
    return data; // {} if the site isn't an onboarding course
  }
}

Build the Lit component

Unlike SakaiTasksWidget (which just wraps a separate inner package), this one fetches and renders directly — the fetch branches on siteId exactly the way SakaiTasks.loadAllData() does.

export class SakaiOnboardingWidget extends SakaiDashboardWidget {

  static properties = { _courses: { state: true }, _course: { state: true } };

  constructor() {
    super();
    this.widgetId = "onboarding-courses";   // drives the title bar
    this.loadTranslations(this.widgetId);    // drives this._i18n
  }

  connectedCallback() { super.connectedCallback(); this.loadData(); }

  loadData() {
    const url = this.siteId
      ? `/api/sites/${this.siteId}/onboarding-courses`
      : "/api/users/me/onboarding-courses";

    fetch(url).then(r => r.json()).then(data => {
      this.siteId ? (this._course = data.course || null)
                    : (this._courses = data.courses || []);
    });
  }

  content() {
    return this.siteId ? this.renderCourse() : this.renderList();
  }
}

Register it — catalog, switch, barrel

Three mechanical additions, each following an existing sibling exactly:

// sakai-onboarding-widget.js — barrel file
import { SakaiOnboardingWidget } from "./src/SakaiOnboardingWidget.js";
customElements.define("sakai-onboarding-widget", SakaiOnboardingWidget);
// SakaiWidgets.js — feeds the "add a widget" picker only
{ id: "onboarding-courses", roles: ["instructor", "student"], tag: "sakai-onboarding-widget" }
// SakaiWidgetPanel.js — the switch that actually renders it
case "onboarding-courses":
  return html`<sakai-onboarding-widget site-id=${...} user-id=${...} ...></sakai-onboarding-widget>`;
